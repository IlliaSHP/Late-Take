# Reanimated: два потоки — фундаментальна логіка

## Звідки назва "Reanimated"

Гра слів навколо вбудованого в React Native API `Animated`. Офіційний опис бібліотеки на GitHub буквально каже: **"React Native's Animated library reimplemented"** — тобто `Animated`, переписаний з нуля на новій архітектурі. Звідси й назва: **Re-** (заново) **+ Animated** (та сама вбудована бібліотека, яку замінили).

# БЛОК 1 — фундамент, обов'язково знати

## 1. Два потоки виконання

У кожному застосунку React Native одночасно працюють два незалежні потоки (це офіційна термінологія React Native, не умовні назви):

- **JS-потік (JavaScript thread)** — тут виконується весь React/JS-код: компоненти, обробники подій, стан.
- **UI-потік (UI thread, часто називають main/головний)** — нативний потік ОС, який малює реальні view на екрані.

Обидва потоки виконуються на пристрої користувача, і обидва належать **саме вашому застосунку** — кожен процес/застосунок має власний UI-потік, це не один потік на весь телефон.

Насправді потоків у застосунку більше (фонові потоки для мережі, для розрахунку layout тощо), але для розуміння анімацій важливі саме ці два.

Як потоки обмінюються даними, залежить від архітектури React Native:
- **стара архітектура**: через **міст (bridge)** — повідомлення серіалізувались у JSON і стояли в черзі, це коштувало часу;
- **нова архітектура** (за замовчуванням з React Native 0.76 / Expo SDK 52): через **JSI** (JavaScript Interface) — JS напряму викликає нативний C++ код, без серіалізації в JSON і черги повідомлень. Сучасні версії Reanimated працюють саме через JSI.

Самі два потоки в новій архітектурі нікуди не зникли: змінився лише спосіб зв'язку між ними.

## 2. Чому не можна анімувати просто через useState

Звичайний шлях (`setState` → React re-render → diff → передача змін у UI-потік → оновлення view) — це весь цей ланцюжок **щокадру**, якщо анімувати стан. Якщо JS-потік у цей момент зайнятий (важкі обчислення, обробка відповіді сервера) — кадр анімації затримується, вона гальмує.

Контенція за потік працює **в обидва боки**: важка логіка гальмує анімацію, і навпаки — важке щокадрове малювання затримує обробку логіки (тапи, мережеві відповіді відчуваються з лагом).

## 3. Чому не можна просто "дати потоку більше потужності"

Один потік виконує інструкції строго послідовно, одну за одною — швидший процесор виконає довгу операцію швидше, але поки вона триває, потік все одно повністю зайнятий і нічого паралельно не робить. Сучасні процесори мають кілька ядер — два потоки можуть виконуватись **справді одночасно**, на різних ядрах. Це не "пріоритет", а реальний паралелізм.

Окремо варто пам'ятати: розділення на потоки вирішує проблему **блокування**, а не проблему швидкості самого заліза. Слабший процесор (менше ядер, нижча тактова частота) все одно виконуватиме кожен окремий потік повільніше — на слабкому пристрої анімації через Reanimated будуть плавнішими, ніж через `useState`, але не миттєвими чи ідеальними самі по собі.

## 4. Це загальний принцип, не тільки React Native

Розділення "потік, що малює, ніколи не блокується" + "все інше окремо" — стандартний патерн у софті загалом: ігрові рушії (render thread окремо від game-logic thread), десктопні GUI-фреймворки (ніколи не блокуй UI-потік), аудіо-рушії (окремий потік з жорсткими часовими вимогами).

**У браузері це теж є** — там роль другого, "малювального" потоку виконує вбудований **compositor-потік**. Різниця в тому, що в браузері це вшито в саму платформу — тому про це майже ніхто не задумується, воно просто працює, коли пишеш `transition` в CSS. У React Native такого вбудованого рішення для анімацій немає, тому й доводиться **імпортувати окрему бібліотеку** (Reanimated) і вручну відтворювати той самий патерн. Детально про браузер — у Блоці 3.

## 5. Reanimated має власну систему реактивності — окрему від React

**Реактивність** — це коли зміна одного значення автоматично тягне за собою перерахунок залежного, без ручного втручання.

У React своя реактивність: змінили `state` → React сам перевиконує функцію компонента → новий JSX. Це завжди веде до **ре-рендеру**.

Reanimated має **свою окрему** систему реактивності, яка не має нічого спільного з React. Коли міняється значення на JS-потоці, ніякого ре-рендеру не відбувається. Замість цього Reanimated сам, на UI-потоці, відстежує, які функції-worklet'и читали це значення, і автоматично перевиконує саме їх — напряму застосовуючи результат до нативного view. Саме завдяки цьому окремому механізму зміна значення одразу відображається на екрані, без жодного проходу через React.

(Що таке worklet і чому в нього особливі правила — у Блоці 2.)

## 6. На UI-потоці працює повноцінна копія JS-двигуна

Reanimated розгортає на UI-потоці не якийсь спрощений виконувач, а **повноцінну копію JS-двигуна** (ще один окремий інстанс, напр. Hermes) — справжнє, самостійне середовище виконання JavaScript, окреме від того, що на JS-потоці, з власною окремою пам'яттю.

Саме тому Babel-плагін мусить "захоплювати" (робити closure) потрібні змінні для worklet-функції — бо це не "та сама функція, показана в іншому місці", а копія, яка має самостійно працювати в абсолютно окремому середовищі, без доступу до пам'яті JS-потоку. Ці захоплені значення залишаються фіксованими там, доки worklet не буде перестворений заново (найчастіше — це ре-рендер компонента).

Важливо: проблема — **не** в тому, щоб один раз передати значення в UI-потік (це просто, одноразова копія). Проблема — в тому, щоб потім це значення можна було **оновлювати**. Саме для цього окремого завдання існує спеціальне сховище значень (`useSharedValue`), яке не копіюється одноразово, а доступне обом потокам, тому завжди актуальне без потреби в новому знімку.

# БЛОК 2 — поглиблено, корисно знати

## 7. Worklet — назва і навіщо вона взагалі потрібна

**Worklet — не "work + let" (дозволяти)**. "-let" — англійський зменшувальний суфікс, як у `booklet`, `piglet`, і найголовніше — `applet` (маленька програма в ізольованому середовищі, звідси й пряма мовна модель). "Worklet" = `work` + `-let` = маленький, ізольований шматочок коду.

Здавалось би — це ж просто той самий JS-код, навіщо окрема назва? Тому що середовище виконання справді інше, і назва про це попереджає:
- виконується у власному, ізольованому JS-середовищі на UI-потоці;
- звичайні зовнішні змінні копіюються одноразовим знімком, а не лишаються живим посиланням (див. нижче — stale closure);
- не має доступу до звичайного контексту компонента, модулів, React.

Тобто це той самий JS-синтаксис, але з іншими правилами гри — тому й інша назва.

## 8. Stale closure на UI-потоці — і як з цим боротись

Сценарій: worklet захопив звичайну (не shared value) змінну, а та згодом змінилась — але без ре-рендеру, який перестворив би worklet заново. UI-потік тоді продовжує працювати зі старою, замороженою копією. Той самий принцип, що й відома проблема stale closure в React-хуках (наприклад, `useEffect` без правильних залежностей), тільки причина інша: не React "забув оновити", а UI-потік банально не має доступу до пам'яті JS-потоку, щоб побачити нове значення.

Як із цим боротись:
- якщо значення, яке потрібне worklet'у, змінюється часто чи незалежно від рендерів — тримайте його не як звичайну змінну, а як shared value — тоді воно завжди актуальне на обох потоках без потреби в новому знімку;
- якщо значення звичайне (проп, похідне число) — переконайтесь, що воно оновлюється через ре-рендер компонента — тоді worklet просто перестворюється заново з кожним рендером, зі свіжим знімком.

## 9. Що таке UIView / View

`View`, який ви імпортуєте (`import { View } from 'react-native'`) — крос-платформний JS-компонент React Native, спільний код для iOS і Android. Але під капотом React Native перекладає його в реальний нативний клас конкретної платформи:

- на iOS це **`UIView`** — базовий клас усіх візуальних елементів у UIKit, нативному UI-фреймворку Apple;
- на Android — **`android.view.View`**, аналогічний базовий клас Android SDK.

Тобто `UIView` — не щось з React Native, а рідний, нативний iOS-клас, у який зрештою перетворюється ваш RN-компонент `View`.

## 10. А що як у пристрою одноядерний процесор?

Логіка не ламається, і це не автоматичний перехід "в один потік". Розподіл коду на потоки — рішення рівня операційної системи, яке існує ще з часів, коли всі процесори були одноядерними (багатоядерність масово з'явилась приблизно з середини 2000-х).

На одному ядрі ОС просто дуже швидко перемикається між потоками (**time-slicing** / витискувальна багатозадачність) — кожному потоку дістається маленький шматочок часу процесора, десятки-сотні разів на секунду, створюючи ілюзію одночасності. UI-потік зазвичай має вищий пріоритет у планувальника ОС саме для відгуку інтерфейсу, тому навіть на одному ядрі отримає свою чергу вчасно частіше, ніж якби розділення на потоки не було взагалі.

Це не так добре, як справжній паралелізм на двох ядрах (контенція за час все одно лишається, дуже важке завдання на JS-потоці все ще може вкрасти чергу в UI-потоку), але це працює, а не ламається. На практиці питання майже суто теоретичне — сучасні смартфони й комп'ютери, навіть бюджетні, вже понад десятиліття всі багатоядерні.

# БЛОК 3 — де і коли існують два потоки

## 11. Потоки створює програма, а не пристрій

Потік це не властивість заліза чи телефона. **Потоки створює сама програма** через операційну систему. Будь-яка сучасна ОС (Android, iOS, Windows, macOS, Linux) дозволяє програмі мати скільки завгодно потоків, на будь-якому пристрої, старому чи новому.

Від заліза залежить тільки одне: чи потоки виконуються **справді одночасно** (кілька ядер), чи по черзі з дуже швидким перемиканням (одне ядро, див. п. 10). Тому "на старих пристроях немає двопотокової системи" — неправильно: потоки є завжди, змінюється лише те, наскільки паралельно вони працюють.

## 12. Коли з'являються два потоки в React Native

**Автоматично, при запуску застосунку. Нічого налаштовувати не треба.**

1. ОС запускає процес застосунку і створює йому **головний (UI) потік**. Так відбувається з **кожним** нативним застосунком на iOS і Android
2. React Native при старті створює **окремий потік для JS** і запускає в ньому JS-двигун (Hermes). Звідти виконується весь твій код

Єдине налаштування стосується Reanimated: його Babel-плагін, який готує worklet'и для UI-потоку. В Expo він підключається автоматично через `babel-preset-expo`.

## 13. Чому в React Native не один потік

На iOS і Android діє жорстке правило: **змінювати інтерфейс можна тільки з головного (UI) потоку**. На Android спроба змінити view з іншого потоку кидає помилку, на iOS UIKit теж вимагає головного потоку.

Якби JS виконувався на головному потоці, будь-яка важка JS-операція (обробка великої відповіді сервера, складний рендер) зупиняла б малювання: застосунок завмирав би, не реагуючи на дотики. Тому React Native свідомо виносить JS в окремий потік. Результат видно на практиці: навіть коли JS-потік зайнятий, нативний скрол `ScrollView` чи `FlatList` продовжує працювати плавно, бо скролом керує UI-потік.

Ціна цього рішення: будь-яка зміна інтерфейсу з JS (зокрема анімація через `useState`) мусить пройти з JS-потоку в UI-потік. Звідси і потреба в Reanimated.

## 14. Які програми мають такий поділ

| Програма | Як влаштовано |
|---|---|
| **Нативні застосунки** (Swift, Kotlin) | головний потік є завжди, і за замовчуванням **і логіка, і UI** виконуються на ньому. Важку роботу розробник виносить у фонові потоки **вручну** (на iOS черги GCD / `async` у Swift, на Android корутини Kotlin) |
| **React Native** | весь JS **завжди** на окремому JS-потоці, UI на головному. Поділ закладений у саму архітектуру |
| **Браузер** | JS і розрахунок сторінки на головному потоці, скрол і частина анімацій на compositor-потоці (п. 15) |
| **Ігрові рушії** (Unity, Unreal) | окремі потоки для рендеру, логіки, фізики, аудіо |

Тобто "два потоки" як обов'язкова структура це особливість **React Native**. Самі потоки є всюди, але розподіляються по-різному.

## 15. Два потоки у браузері

У браузері для кожної сторінки є:
- **головний потік (main thread)**: JS сторінки, розрахунок стилів, layout (розміри і позиції елементів), paint (підготовка того, що малювати)
- **compositor-потік**: складає готові шари сторінки в кадр і виводить на екран. Тут же обробляється **скрол**

Що це означає на практиці:
- CSS-анімації і transition властивостей **`transform` і `opacity`** браузер може виконувати на compositor-потоці: вони лишаються плавними, навіть коли JS зайнятий
- анімації **`width`, `height`, `top`, `left`, `margin`** вимагають перерахунку layout на кожному кадрі, а layout на **головному потоці** разом з JS: коли JS зайнятий, такі анімації гальмують
- анімація, яку JS рухає сам на кожному кадрі (`requestAnimationFrame` + зміна стилів), теж повністю на головному потоці

Тому твоє розуміння майже правильне: більшість роботи зі стилями у вебі справді на одному потоці з JS, крім compositor-властивостей і скролу. Звідси загальна порада вебу: **анімувати `transform` і `opacity`**.

Додаткові потоки у вебі є ще два типи:
- **Web Workers**: окремі потоки для JS, але **без доступу до DOM**. Підходять для важких розрахунків, не для анімацій інтерфейсу
- **Animation Worklet** (частина CSS Houdini): спроба дати вебу те саме, що Reanimated, тобто власний JS-код анімації поза головним потоком. Ця технологія **не прижилась**: вона з'явилась лише експериментально в браузерах на Chromium, інші браузери її не підтримали

До речі, **Reanimated у вебі** (якщо RN-застосунок запускають як сайт через react-native-web) окремого UI-потоку не має: worklet'и там виконуються на головному потоці разом з рештою JS.

## 16. Чому сайти часто лагають сильніше за застосунки

Потоки пояснюють частину різниці, але не всю.

**Що дають потоки.** У нативному застосунку текстове поле це нативний компонент, введення тексту обробляє ОС на головному потоці застосунку, навіть якщо логіка застосунку в цей момент зайнята. У вебі кожне натискання клавіші проходить через головний потік сторінки, де ж виконується весь JS і перерахунок сторінки. Якщо JS зайнятий (наприклад, обробкою відповіді, що приходить по частинах, чи рендером розмітки довгої відповіді), введення відчувається з затримкою.

**Інші причини**, які часто важать більше:
- **розмір сторінки**: довгий чат з сотнями повідомлень це тисячі DOM-елементів; кожна зміна змушує браузер перераховувати стилі і layout. Мобільні застосунки зазвичай малюють тільки видиму частину списку (як `FlatList`), сайти часто малюють усе
- **розширення браузера**, які виконують свій код на кожній сторінці
- **сам браузер** як програма споживає багато пам'яті й процесора, особливо з багатьма вкладками

Тож приклад з ChatGPT узгоджується з логікою потоків: введення в нативному полі не залежить від зайнятості логіки, а у вебі залежить. Але велику роль там, найімовірніше, грає і розмір сторінки з довгою історією чату.

## 17. Як пояснити на співбесіді

У React Native JS-код виконується на окремому JS-потоці, а нативний інтерфейс малюється на головному UI-потоці, бо iOS і Android дозволяють змінювати view тільки з головного потоку. React Native створює цей поділ автоматично при запуску. Будь-яка зміна інтерфейсу з JS мусить перейти з JS-потоку в UI-потік: у старій архітектурі через bridge, у новій через JSI. Якщо анімувати через `setState`, кожен кадр проходить через JS-потік, і коли він зайнятий, анімація гальмує. Reanimated вирішує це тим, що виконує код анімації (worklet'и) прямо на UI-потоці в окремому JS-рантаймі, а значення передає через shared values, тому анімація не залежить від зайнятості JS-потоку.

У вебі схожу роль виконує compositor-потік браузера: він обробляє скрол і анімації `transform` та `opacity` незалежно від головного потоку, де виконується JS і layout.
