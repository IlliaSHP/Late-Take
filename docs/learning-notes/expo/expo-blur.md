## Sticky-хедер з блюром (expo-blur, Reanimated, Android)

Контекст: хедер поверх скролу, який при скролі плавно "проявляється" — стає розмитим і затемненим.

### 1. Блюр завжди статичний — анімується лише прозорість обгортки

`BlurView` сам ніколи не отримує анімовані пропси (`intensity` завжди фіксована). Анімується `opacity` звичайного `Animated.View`, всередині якого лежить статичний `BlurView`.

```tsx
// ❌ Ненадійно — анімується сам BlurView
const AnimatedBlur = Animated.createAnimatedComponent(BlurView)
<AnimatedBlur style={[StyleSheet.absoluteFill, blurStyle]} />

// ✅ Надійно — анімується обгортка, BlurView статичний
<Animated.View style={[StyleSheet.absoluteFill, blurStyle]}>
  <BlurView intensity={80} tint='...' style={StyleSheet.absoluteFill} />
</Animated.View>
```

**Чому саме так:** пряма анімація `opacity` у `BlurView` через `createAnimatedComponent` ненадійна — задокументована історія проблем саме з цим у changelog `expo-blur` (запис про заміну "non-working alpha-based blur mechanism" на iOS). Звичайний `View` реагує на зміну `opacity` завжди коректно. Коли міняється `opacity` батьківського елемента — усе всередині нього стає пропорційно менш/більш видимим, незалежно від того, що саме там лежить. Тому результат той самий: сила блюру фіксована, змінюється лише те, чи видно його крізь обгортку.

### 2. Порядок компонентів у JSX

`BlurTargetView` — нативний елемент, який фізично "фотографує" те, що під ним, для розмиття. `BlurView` бере цю фотографію через `blurTarget`.

Нативний рушій Android будує дерево екранних елементів у тому порядку, в якому вони йдуть у JSX. Якщо `BlurView` (усередині хедера) стоїть вище за `BlurTargetView` в коді — нативний елемент-мішень ще не існує в дереві на момент, коли `BlurView` намагається до нього прив'язатись. Нема чого фотографувати.

```tsx
// ❌ Хедер написаний вище за контент
<Screen>
  <HomeHeader .../>
  <BlurTargetView ref={blurTargetRef}>
    <Animated.ScrollView>...</Animated.ScrollView>
  </BlurTargetView>
</Screen>

// ✅ Хедер написаний нижче за контент
<Screen>
  <BlurTargetView ref={blurTargetRef}>
    <Animated.ScrollView>...</Animated.ScrollView>
  </BlurTargetView>
  <HomeHeader .../>
</Screen>
```

Позиція на екрані не міняється (хедер усе одно `position: absolute`), змінюється лише порядок рядків коду.

**Важливо:** саме по собі перестановлення без реального `blurTarget`-зв'язку (реф) не рятує — потрібні обидві речі одночасно: правильний порядок і сам зв'язок через реф.

**Веб-аналогія не працює тут:** CSS `backdrop-filter: blur()` не має цієї проблеми — браузерний композитор сам, у реальному часі, бере піксель, що фізично лежить позаду елемента, незалежно від порядку в DOM, без явної цілі. `expo-blur` на Android — не системна фіча ОС (як `UIVisualEffectView` на iOS), а бібліотека-обхідний шлях, яка вручну "фотографує" позначений елемент через ref — тому й чутлива до порядку дерева. Це квірк конкретно цієї Android-техніки, не React Native загалом.


### 3. Затримки при скролі — два окремі явища

**Загальна причина затримки в scroll-driven анімаціях Reanimated (підтверджено, issue #160 в `software-mansion/react-native-reanimated`):** значення, похідні від скролу, обробляються через чергу, яка запитує в ОС `requestAnimationFrame`, а не оновлюються напряму на кожну подію. Під час простою ОС може "приспати" цей цикл заради економії батареї — перший скрол після паузи йде на пробудження циклу, тому має невелику затримку. Це загальна властивість будь-яких scroll-driven анімацій у Reanimated, не специфічна для блюру.

**Окреме, не до кінця підтверджене явище, специфічне саме для блюру:** спостерігалась інша, конкретніша поведінка — під час **безперервного** скролу від самого початку блюр не з'являвся взагалі. Лише коли скрол **зупинявся** (не просто уповільнювався, а справді зупинявся) нижче початкової точки і минало кілька секунд — блюр з'являвся, і після цього продовжував плавно оновлюватись при подальшому безперервному скролі, включно з поверненням до самого верху без зупинок. Повторна зупинка на самому верху на кілька секунд знову "скидала" цей стан.

Це виглядає як вимога **реальної зупинки руху** для першого запуску розрахунку блюру, а не просто "вихід з простою" — тобто не повністю пояснюється чергою вище. Точний механізм **не підтверджений** офіційною документацією чи джерелом — це відтворення спостереженої поведінки, а не задокументований факт. Якщо ця поведінка повториться в майбутньому — варто перевірити, чи вона й досі актуальна після додавання `blurTarget`/маски.

### 4. Вимога Android 12+ і fallback для старих версій

Справжній блюр на Android доступний лише через `RenderNode API`, який з'явився в Android 12 (SDK 31). На старіших версіях `blurMethod='dimezisBlurViewSdk31Plus'` автоматично падає назад на `'none'` — тобто взагалі без блюру, лишається тільки той шар, що всередині (наприклад, лінійний градієнт).

**Проблема:** якщо всередині лишити тільки темний `LinearGradient` без справжнього блюру позаду — на старому Android градієнт нічого не "прикриває" й виглядає як непояснене затемнення без функції.

**Перевірка версії:**
```tsx
import { Platform } from 'react-native'

const hasRealBlur =
  Platform.OS === 'ios' ||
  (Platform.OS === 'android' && Platform.Version >= 31)
```
(`Platform.Version` на Android — число, напряму API-рівень; 31 = Android 12.)

**Гілка з фолбеком:**
```tsx
{hasRealBlur ? (
  <MaskedView ...>
    <BlurView .../>
    <LinearGradient .../>
  </MaskedView>
) : (
  <View style={styles.overlay} />   {/* суцільний темний прямокутник, без блюру й без маски */}
)}
```

**`MaskedView` на старому Android:** технічно не ламається — йому байдуже, що саме всередині (блюр чи fallback-прямокутник), маскує будь-який вміст за прозорістю однаково. Проблема не технічна, а дизайнерська: без реального блюру позаду контрасту під текстом хедера може не вистачати, якщо той самий шар ще й розчинити донизу маскою. Тому на старих версіях простіше лишити суцільний непрозорий `overlay` замість маскованого градієнта.

### 5. Синтаксис

```tsx
<BlurView
  intensity={80}                              // сила блюру, 0–100, завжди фіксована
  tint='systemChromeMaterialDark'              // тонування (iOS-специфічні системні варіанти теж працюють)
  blurTarget={blurTargetRef}                   // реф на BlurTargetView — що саме розмивати (Android)
  blurMethod='dimezisBlurViewSdk31Plus'        // метод блюру на Android
  style={StyleSheet.absoluteFill}
/>
```

**`blurMethod` — значення:**
- `'none'` (default) — fallback: напівпрозорий `View`, не справжній блюр
- `'dimezisBlurView'` — справжній блюр на всіх версіях Android, може просідати по продуктивності на SDK 30 і нижче
- `'dimezisBlurViewSdk31Plus'` — справжній блюр лише на SDK 31+ (Android 12+), автоматичний fallback на `'none'` нижче

**`BlurTargetView` + `blurTarget`:**
```tsx
const blurTargetRef = useRef<View>(null)

<BlurTargetView ref={blurTargetRef}>
  <Animated.ScrollView>...</Animated.ScrollView>
</BlurTargetView>

<BlurView blurTarget={blurTargetRef} .../>
```
Реф типізується як `RefObject<View | null>` — реф завжди починається з `null` (елемент ще не змонтований), а після монтування React сам підставляє реальний `View`. Тип має описувати обидва стани.

**На iOS ці пропси нічого не роблять — і це безпечно.** `blurTarget`, `blurMethod`, `BlurTargetView` — специфіка тільки для Android (там справжній блюр — системна фіча ОС через `UIVisualEffectView`, окремий механізм-обхід не потрібен). Можна лишати ці пропси в коді завжди, без перевірки платформи — на iOS вони просто ігноруються.
