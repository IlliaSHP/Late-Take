## Expo Go vs dev client, ліміти EAS Build

### Коли Expo Go вистачає, а коли ні

**Expo Go** — один загальний застосунок від Expo, заздалегідь зібраний з фіксованим набором нативних модулів. Запускає код будь-якого Expo-проєкту миттєво, без збірки — але тільки поки проєкт не використовує нічого нативного поза тим, що вже вшите в Expo Go.

Офіційні пакети Expo (`expo-blur`, `expo-linear-gradient` тощо) зазвичай позначені як "Included in Expo Go" — вони автоматично доступні у версії, що збігається з SDK проєкту, тому їх можна тестувати прямо в Expo Go без збірки.

**Dev client** потрібен, коли в проєкт додається **стороння** нативна залежність (не з офіційного набору Expo) — щось, чого немає у фіксованому наборі Expo Go. Якщо відкрити такий застосунок у звичайному Expo Go — відповідний функціонал просто не покаже нічого або не працюватиме, бо середовище Expo Go підтримує лише те, що в ньому спочатку встановлено.

**Dev client** — власний застосунок, зібраний спеціально під конкретний проєкт, з саме тими нативними модулями, які потрібні. У день-у-день роботі відчувається ідентично Expo Go (той самий "відскануй QR, редагуй код, бач зміни одразу"). Різниця проявляється лише коли додається/міняється щось нативне — тоді для Expo Go це показати неможливо в принципі, а dev client вимагає нової збірки (бо це власна збірка під проєкт).

**Альтернатива без хмари:** можна встановити Android SDK/Android Studio локально й збирати через `expo run:android`. Dev client через хмару (EAS Build) — простіше для слабкого ноутбука: усе навантаження на чужих серверах, середовище вже налаштоване, є безкоштовний тариф.

### Ліміти безкоштовного плану EAS Build

- **15 Android-збірок і 15 iOS-збірок на місяць**, лічильник скидається щомісяця
- Нижчий пріоритет у черзі порівняно з платними планами (можна почекати довше)
- **45 хвилин — максимальний час на ОДНУ збірку**, а не ліміт часу використання застосунку на день. Якщо компіляція не вклалась у 45 хв — обривається як невдала. До використання вже встановленого `.apk` це не має жодного стосунку.

**Як це працює на практиці:**
1. `eas build` — витрачає одну збірку з місячного ліміту, займає якийсь час (черга + компіляція)
2. Отриманий `.apk` встановлюється на телефон **один раз**
3. Щодня далі — просто `expo start --dev-client`, відкривається вже встановлений застосунок (не Expo Go — власна іконка), підключається до dev-сервера так само, як Expo Go. Це можна робити необмежено, без нових збірок — JS/TSX-код підхоплюється миттєво через Metro
4. Нова збірка знадобиться лише коли з'являється/змінюється нативний код — новий пакет, нова версія нативного модуля, зміна нативного конфіга

### Орієнтир встановлення (коротко)

```
pnpm --filter mobile install-client  # (умовно — реальні кроки нижче)
```

1. Встановити `expo-dev-client`:
   ```
   pnpm --filter mobile exec expo install expo-dev-client
   ```
2. Встановити `eas-cli` як dev-залежність (не глобально — щоб версія була прив'язана до проєкту):
   ```
   pnpm --filter mobile add -D eas-cli
   ```
3. Увійти в акаунт Expo:
   ```
   pnpm --filter mobile exec eas login
   ```
4. Налаштувати проєкт і профілі збірки:
   ```
   pnpm --filter mobile exec eas build:configure
   ```
   Створює/оновлює `eas.json`. Профіль `development` має містити `developmentClient: true` і `distribution: internal`.
5. Запустити збірку:
   ```
   pnpm --filter mobile exec eas build --profile development --platform android
   ```
6. Встановити отриманий `.apk` на телефон (посилання/QR у виводі команди)
7. Щодня далі:
   ```
   pnpm --filter mobile exec expo start --dev-client
   ```

**Про `.gitignore`:** `eas login` не зберігає нічого в папці проєкту — токен авторизації лежить у глобальній конфігурації поза репозиторієм. `eas.json` нормально комітити, секретів там немає. Стандартно варто мати в `.gitignore`: `.expo/`, `*.p12`, `*.jks`, `*.keystore`, `credentials.json`, `.env*`.
