# Reanimated: хуки та spring-анімації

База — `react-native-threading-model.md` (два потоки, міст, воркліти). Тут — конкретні інструменти бібліотеки, які цією архітектурою користуються.

---

## useSharedValue

```js
const scale = useSharedValue(1)
```

Хук для зберігання значення, яке відразу доступне в обох потоках (thread) — JS і UI — без мосту між ними. JS-потік лише зрідка записує нове цільове значення (наприклад, по натисканню), а UI-потік читає його щокадру, щоб намалювати поточний стан.

Це потрібно, щоб Reanimated міг працювати з цим значенням прямо на UI-потоці: якщо тримати і логіку, і анімацію в одному (JS) потоці, все сповільнюється — анімації тормозять, а сама логіка теж виконується довше, бо змагається за той самий потік.

Звичайні захоплені (closure) значення при перенесенні коду на інший потік копіюються одноразово, як знімок на момент створення — тому вони "застигають" і самі не оновлюються. `useSharedValue` навмисно зроблений інакше: значення не копіюється одноразово, а живе в пам'яті, видимій з обох потоків одразу, — тому завжди актуальне на обох, без потреби в новому знімку щоразу.

Перший (JS) потік і так завжди спілкується з другим (UI) потоком — щось же має малювати екран, і цей UI-потік відповідає за відмалювання завжди, на будь-якому пристрої. Зазвичай дані передаються через міст (bridge), а це не супершвидко. Тому Reanimated замість цього запускає свої скрипти (воркліти — ті самі звичайні js-скрипти, просто виконуються на UI-потоці) прямо там: розгортає туди маленьку копію JS-двигуна й виконує вже готовий код воркліта (Babel лише позначає й готує цей код одноразово під час збірки застосунку — на телефоні в рантаймі Babel не бере участі). Завдяки цьому логіка анімації рахується там же, де й має врешті застосуватись, а не в JS-потоці з подальшою витратою часу й ресурсів на передачу результату через міст.

UI-потік — не щось специфічне для анімацій, а взагалі відповідає за відмалювання всього інтерфейсу самого застосунку (не всього пристрою — у кожного застосунку свій власний UI-потік). Такий поділ на "потік логіки" й "потік відмальовування" — загальний архітектурний принцип, який є і в нативній Android/iOS-розробці, і в геймдеві, і в десктопних GUI-фреймворках.

**Синтаксис:**
```js
const value = useSharedValue(initialValue)

value.get()          // читання (на будь-якому потоці)
value.set(newValue)  // запис — миттєвий або через with*-функцію (нижче)
```

Може зберігати не тільки числа — рядки (`'#ffffff'`, `'10deg'`), булеві, об'єкти (`{ x: 0, y: 0 }`), масиви. Не може зберігати функції чи класи.

### Старий запис — `.value`

До `.get()`/`.set()` (і досі підтримується) читання й запис відбувались як звичайна властивість об'єкта:
```js
scale.value = withSpring(0.95)
console.log(scale.value)
```
Це працює, але вважається застарілим стилем. Причина: `.value` виглядає точнісінько як звичайне поле React-стану чи будь-якого об'єкта — і це може заплутати інструменти, які аналізують код за патерном доступу через крапку (наприклад, React Compiler — інструмент, що автоматично оптимізує компоненти, дивлячись, які властивості вони читають). Побачивши `scale.value`, такий інструмент може подумати "це React-реактивне значення, треба стежити за ним для ре-рендеру" — хоча насправді це геть чужа, reanimated-івська система реактивності. Явний виклик методу (`scale.get()`) одразу сигналізує "тут щось особливе, це не проста властивість" — і такі інструменти це просто оминають.

**Це загальніший принцип, не тільки тут.** У світі реактивних бібліотек є справжній розкол саме навколо цього питання: читати "магічне" значення через властивість (`.value`) чи через виклик функції (`()`)? Обидва підходи використовуються свідомо:
- **SolidJS**: сигнали читаються буквально через виклик — `count()`, а не `count.value`. Це навмисне рішення авторів бібліотеки: виклик функції візуально сигналізує "тут відбувається щось особливе (підписка на реактивність)", тоді як звичайна властивість виглядає пасивно.
- **Vue**: `ref()`, навпаки, читається саме через `.value` (через Proxy під капотом) — і це якраз джерело того самого типу плутанини: люди забувають, що `.value` — не проста властивість, а щось, що вимагає особливої обробки (у шаблонах Vue навіть автоматично "розгортає" `.value` за вас — саме через цю плутанину).

Reanimated переходом на `.get()`/`.set()` фактично рухається в бік підходу SolidJS — явний виклик функції як спосіб чесно показати: тут не проста властивість, обережніше.

## useAnimatedStyle

```js
const animated = useAnimatedStyle(() => ({
  transform: [{ scale: scale.get() }]
}))
```

`useSharedValue` створює значення-джерело, з яким можна взаємодіяти напряму через `.get()`/`.set()` (з обох потоків, без мосту). `useAnimatedStyle` — автоматичний спостерігач: не має власних `get`/`set`, а сам, самостійно перераховує стиль щоразу, коли джерело змінюється. Напряму з результатом `useAnimatedStyle` ніколи не взаємодіють — тільки міняють джерело (shared value), а стиль підхоплює зміну сам.

Правило перерахунку стилю з джерела: коли `scale` (shared value) змінюється, ця функція перевиконується сама, на UI-потоці, без участі React і без ре-рендеру компонента.

**Розбір синтаксису:**
- `() => ( ... )` — скорочений вигляд функції, де круглі дужки одразу повертають те, що всередині (замість `return { ... }`). `{ ... }` всередині — це об'єкт стилю RN.
- `transform` — стандартна властивість стилю React Native (аналог CSS `transform`), яка вимагає саме масив об'єктів: `[{ scale: ... }, { rotate: ... }]`. Це вимога самого RN, а не Reanimated — Reanimated нічого свого не вигадує, просто підставляє живе число в ту саму структуру, яку й так очікує RN. Кожен об'єкт масиву називає конкретний вид трансформації (`scale`, `rotate`, `translateX`...) — так само, як у CSS `transform: scale() rotate()`. Порядок у масиві впливає на результат.
- `scale.get()` — читає поточне значення shared value, доступне на обох потоках без мосту.

## Animated.createAnimatedComponent
 
```js
const AnimatedPressable = Animated.createAnimatedComponent(Pressable)
```
 
Третя, завершальна ланка картини: `useSharedValue` тримає значення на обох потоках → `useAnimatedStyle` рахує з нього "живий" стиль на UI-потоці → а конкретний нативний компонент має вміти **прийняти** цей живий стиль і застосовувати його оновлення напряму, минаючи React. Звичайний компонент цього не вміє — він очікує в `style` статичний, один раз порахований об'єкт. `createAnimatedComponent` бере звичайний RN-компонент і повертає "підключену" версію, здатну приймати результат `useAnimatedStyle`.
 
Це **не** те, що RN-теги вміють за замовчуванням — сам React Native нічого не знає про "живі" стилі Reanimated, і звичайний `View` (як і будь-який інший неанімований компонент) кине помилку, якщо дати йому "живий" стиль з `useAnimatedStyle`. Просто Reanimated заздалегідь сам обгорнув кілька найпоширеніших компонентів і експортує їх готовими: `Animated.View`, `Animated.Text`, `Animated.Image`, `Animated.ScrollView` — ними можна користуватись одразу. Усе, що поза цим списком (як `Pressable`), доводиться обгортати самостійно, один раз.

**Важливо не плутати:** `Animated.View` — це вже готовий, наперед обгорнутий експорт, а не звичайний `View` з якоюсь особливою вбудованою здатністю. Тобто ці два записи означають рівно те саме:

​```js
const AnimatedView = Animated.createAnimatedComponent(View)
// те саме, що просто:
Animated.View
​```

Обгортати `View` вручну через `createAnimatedComponent` — зайве, він і так вже є в бібліотеці готовим. А ось звичайний `View`, імпортований напряму з `'react-native'` (не з `Animated`), "живих" стилів так і не приймає — саме тому спроба дати такий стиль голому `View` кидає помилку.
 
Обгортку роблять на рівні модуля, а не всередині функції компонента — так само, як з класами чи функціями, які варто виносити за межі компонента, щоб не створювати нове посилання щорендеру.

## withSpring

```js
scale.set(withSpring(toValue, config, callback))
```

Не присвоює значення миттєво — плавно анімує до цілі за фізикою пружини, на UI-потоці.

### Параметри пружини

| Параметр | Default | Що робить |
|---|---|---|
| `stiffness` | `100` | жорсткість — сила тяги до цілі. Вища → рух швидший і різкіший |
| `damping` | `10` | гальмування — як швидко затухають коливання. Вищий → менше відскоку, швидше зупиняється |
| `mass` | `1` | інерція — "вага" об'єкта. Вища → повільніший старт і зупинка, відчуття важкості |

**Комбінації для порівняння:**

| Назва | stiffness | damping | mass | Відчуття |
|---|---|---|---|---|
| Дефолт | 100 | 10 | 1 | помірний, легкий відскок |
| Чітко, без відскоку | 250 | 25 | 1 | ділово, "клац" |
| Соковитий bounce | 150 | 6 | 1 | помітно пружинить, живо |
| Важкий | 80 | 12 | 4 | ніби тягне щось важке |
| Миттєвий | 300 | 20 | 0.4 | різкий, легкий відгук |

Є вбудований іменований пресет: `GentleSpringConfig` — `{ damping: 120, mass: 4, stiffness: 900 }`, можна одразу `withSpring(1, GentleSpringConfig)`.

### Альтернативний конфіг (не мішати зі stiffness/damping)

```js
withSpring(1, { duration: 500, dampingRatio: 0.5, clamp: { min: 0, max: 1.2 } })
```
`duration` (мс) + `dampingRatio` (0–1, де 1 = без відскоку) — той самий рух, описаний через час замість фізики. `clamp` обмежує межі руху.

### Колбек завершення

```js
withSpring(1, config, (finished, current) => {
  if (finished) {
    // finished === false, якщо анімацію перервали новим .set()
  }
})
```

Третій аргумент **автоматично стає worklet і виконується на UI-потоці**. Щоб зсередини нього викликати звичайну JS-функцію (навігація, зміна React-стану, haptics) — потрібен `runOnJS(fn)()`, який перекидає виклик назад у JS-потік:

```js
import { runOnJS } from 'react-native-reanimated'

withSpring(1, config, (finished) => {
  if (finished) {
    runOnJS(someJsFunction)()
  }
})
```

(Директиву `'worklet'` вручну писати не обов'язково саме тут — Babel і без неї автоматично позначає цей колбек як worklet, бо це одне з "відомих" йому місць.)

## Споріднені функції

Та сама форма (значення → конфіг → колбек), різна фізика руху:

| Функція | Що робить |
|---|---|
| `withTiming(toValue, { duration, easing })` | фіксований час + крива уповільнення (`Easing`), без фізики |
| `withDecay({ velocity, deceleration, clamp })` | інерція/тертя — для свайпів, флік-жестів |
| `withSequence(anim1, anim2, ...)` | виконує анімації одну за одною на тому самому shared value |
| `withDelay(ms, animation)` | відкладає старт іншої анімації |
| `withRepeat(animation, numberOfReps, reverse)` | повторює; `-1` = нескінченно, `reverse: true` = туди-сюди ("йо-йо") |

**Overshoot** — коли значення проскакує повз ціль перед тим, як осісти (реальні пружини так і рухаються). Робиться через `withSequence`:

```js
scale.set(withSequence(withSpring(1.05), withSpring(1)))
```

Спочатку анімує до `1.05` (більше за норму), і тільки коли ця анімація повністю дограє — стартує друга, до `1`.

Усе комбінується довільно: `withDelay(200, withSpring(1))`, `withRepeat(withSequence(withTiming(1.03, { duration: 500 }), withTiming(1, { duration: 500 })), -1, true)` — нескінченний м'який пульс.
