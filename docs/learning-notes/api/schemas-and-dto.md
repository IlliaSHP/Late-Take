# Схеми і DTO

## Схема загалом у програмуванні

**Схема це опис того, як мають виглядати дані** (часто разом з правилами). Це не термін якоїсь бібліотеки, а загальне слово. Бувають різні схеми, залежно від того, **які** дані описуються:

| Вид схеми | Що описує | Де в проекті |
|---|---|---|
| **Схема валідації** | правила перевірки даних | фронт: Zod (`packages/schemas`); бек: правила в DTO-класах через бібліотеку class-validator |
| **Схема бази даних** | таблиці і колонки в базі | бек: Prisma, файли `prisma/schema/*.prisma` |
| **Схема API** | як виглядають дані в запитах і відповідях | розділ `components.schemas` в `openapi.json` |

Слово одне, рівні різні. Суть завжди: як виглядають дані.

Для схем валідації на фронті є кілька бібліотек: **Zod, Yup, Valibot, ArkType**. Кожна створює схеми своїм синтаксисом. Zod можна використовувати і на беку.

Про Zod-схеми детально: [../forms/zod.md](../forms/zod.md).

## DTO (Data Transfer Object)

**DTO це опис даних, які передаються між частинами програми** (найчастіше між фронтом і беком): які поля і якого типу.

- **Data**: дані
- **Transfer**: передача (по мережі між фронтом і беком)
- **Object**: об'єкт з полями

Навіщо: фронт і бек це дві окремі програми, часто їх пишуть різні люди. DTO це контракт: «на цей ендпоінт шли ось такі поля».

DTO описує тільки **форму даних**. Що бек з ними робить, у DTO не написано: це логіка бекенду.

### Загальний патерн

DTO не прив'язаний до мови чи фреймворку: Java (Spring), C# (ASP.NET), PHP (Laravel), Python (у FastAPI це Pydantic-моделі), Node.js (NestJS). Мова різна, ідея та сама.

### Request і Response

- **request DTO**: що бек **приймає**. У бекенді проекту лежать у папках `dto/`: `RegisterDto`, `LoginDto`, `CollectionTitlesDto`
- **response DTO**: що бек **повертає**. У бекенді проекту лежать у папках `response/` і називаються `...Response`: `AuthResponse`, `CollectionResponse`

### DTO на беку і на фронті

Один і той самий DTO існує **у двох місцях**:

```
Бекенд: src/auth/dto/login.dto.ts                     ← оригінал (class), пише бекенд-розробник
           ↓ через openapi.json
Фронт:  packages/api/src/generated/models/loginDto.ts ← копія (interface), згенерована Orval
```

**На беку** це клас з полями і правилами перевірки:

```ts
// бекенд: login.dto.ts
export class LoginDto {
  @IsEmail({}, { message: 'Invalid email' })   // правило: має бути email
  readonly email: string

  @MinLength(6, { message: 'Password must be at least 6 characters' })  // правило: мінімум 6
  readonly password: string
}
```

Рядки з `@` це правила перевірки з бібліотеки class-validator. Бек перевіряє ними кожен запит.

Клас, а не interface, бо бекенду треба перевіряти дані в рантаймі, а інтерфейси й типи після компіляції зникають. Клас існує і в звичайному JS.

**На фронті** це interface, який згенерував Orval:

```ts
// фронт: generated/models/changePasswordDto.ts
/**
 * Generated by orval 🍺
 * Do not edit manually.
 */
export interface ChangePasswordDto {
  /**
   * @minLength 6
   * @maxLength 100
   */
  oldPassword: string;
  /**
   * @minLength 6
   * @maxLength 100
   */
  newPassword: string;
}
```

Коментарі `@minLength` прийшли з правил на бекенді через `openapi.json`. Самі правила фронтовий interface не перевіряє, це просто підказка. «Do not edit manually»: при наступній генерації файл перезапишеться.

Interface, а не `type`, бо Orval так генерує за замовчуванням. Для опису об'єкта `interface` і `type` майже однакові.

### Роль DTO, якщо Orval усе генерує

DTO це **джерело**. Orval нічого не вигадує, він копіює DTO з бекенду. Нема DTO на беку → нема схеми в `openapi.json` → нема типу на фронті.

## DTO проти Zod-схеми

| | DTO на фронті | Zod-схема |
|---|---|---|
| Питання | які поля і якого типу | чи правильно заповнені дані |
| Що це | тип (interface) | значення (об'єкт з правилами) |
| Коли існує | тільки під час написання коду | коли застосунок працює |
| Перевіряє дані | ні | так |
| Правила | тільки типи полів | типи + формат email, мінімум символів тощо |

Зв'язок між ними в `auth.ts`: `satisfies z.ZodType<RegisterDto>` перевіряє, що схема дає рівно ті поля, що в DTO (див. [../javascript-typescript/satisfies.md](../javascript-typescript/satisfies.md)).

Правила перевірки в проекті існують двічі:
- **фронт** (Zod): щоб показати помилку одразу під полем, без запиту на сервер
- **бек** (class-validator у DTO): обов'язково, бо запит можна відправити в обхід фронта (Postman, curl)

Тому навіть тексти помилок однакові:

```ts
// бек, login.dto.ts
@IsEmail({}, { message: 'Invalid email' })

// фронт, auth.ts
email: z.email('Invalid email')
```
