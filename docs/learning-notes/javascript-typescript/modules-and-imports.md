# Що відбувається при імпорті файлу

Це поведінка **JavaScript-модулів** (ES modules). Однаково працює в браузері, Node.js і React Native.

## Головне правило

**Коли файл імпортують уперше, JS проходить його зверху вниз і виконує весь код на верхньому рівні файлу.**

Верхній рівень = код, який не всередині функції.

## Оголошення проти виклику

- **оголошення** функції тільки створює її. Код **всередині** функції не виконується, поки її не викличуть
- **виклик** функції виконується одразу, і тоді виконується її тіло

```ts
// file.ts
console.log('1')                  // виконається одразу

const sayHi = () => {
  console.log('Hi')               // НЕ виконається: тіло функції, її ще не викликали
}

console.log('2')                  // виконається одразу

sayHi()                           // виклик на верхньому рівні → виконається console.log('Hi')
```

```ts
// інший файл
import './file'
// у консолі: 1, 2, Hi
```

## Файл виконується тільки один раз

Якщо той самий файл імпортують у десяти місцях, його код виконається **один раз**, при першому імпорті. Решта імпортів отримують уже готовий результат.

## Змінні на верхньому рівні файлу

Змінні, оголошені на верхньому рівні файлу:
- живуть весь час, поки працює застосунок
- існують в **одному екземплярі**: усі файли, що імпортують цей файл, працюють з тими самими змінними. Змінилась змінна → усі бачать нове значення

**Важливо: з іншого файлу імпортовану змінну перезаписати не можна.** Імпорти тільки для читання. Змінити змінну може лише код усередині її файлу. Тому для зміни роблять експортовану функцію:

```ts
// counter.ts
export let count = 0
export const increment = () => { count++ }
```

```ts
// a.ts
import { count, increment } from './counter'

count = 5      // ❌ помилка: імпорт тільки для читання
increment()    // ✅ функція з counter.ts змінює count у своєму файлі
```

```ts
// b.ts
import { count } from './counter'
console.log(count)   // 1 - бачить зміну, зроблену з a.ts
```

## У проекті: http.ts і api.ts

`packages/api/src/http.ts`:

```ts
let getToken: () => Promise<string | null> = async () => null
let baseUrl = ''

export const configureApi = (options: { ... }) => {
  baseUrl = options.baseUrl
  getToken = options.getToken
}
```

`getToken` і `baseUrl` на верхньому рівні файлу і навіть не експортовані. Змінити їх можна тільки через `configureApi`, бо вона оголошена в тому самому файлі. Цією ж змінною `baseUrl` потім користується `http` у тому ж файлі.

`apps/mobile/src/lib/api.ts`:

```ts
import * as SecureStore from 'expo-secure-store'   // 1. підвантажити бібліотеку
import { configureApi } from '@app/api'            // 2. підвантажити http.ts (там оголошена configureApi)

configureApi({ ... })                              // 3. ВИКЛИК на верхньому рівні → виконується одразу
```

Функцій у `api.ts` не оголошено, є тільки **виклик**. Він стоїть на верхньому рівні, тому виконується, щойно файл імпортують. А тіло `configureApi` (у `http.ts`) виконується, бо його викликали.

```
старт застосунку
  → _layout.tsx імпортує api.ts: import '@/lib/api' (імпорт заради побічного ефекту, див. нижче)
  → виконується api.ts → викликається configureApi(...)
  → у http.ts змінні baseUrl і getToken перезаписуються

будь-коли пізніше
  → хук Orval викликає http(...)
  → http бере вже збережені baseUrl і getToken
```

Якщо `api.ts` ніде не імпортований, `configureApi` не виконається, `baseUrl` залишиться `''`, і всі запити будуть падати.

## Види імпортів

```ts
import { configureApi } from '@app/api'          // іменований: взяти конкретний експорт за назвою
import Button from '@/components/ui/Button'       // default: те, що експортовано через export default
import * as SecureStore from 'expo-secure-store' // усі експорти файлу, зібрані в один об'єкт
import type { RegisterDto } from '@app/api'       // тільки тип; у фінальному JS рядок зникає
import '@/lib/api'                                // нічого не брати, тільки виконати файл
```

Останній варіант називається **імпорт заради побічного ефекту** (side-effect import): файл потрібен не заради того, що він експортує, а заради коду, який у ньому виконується.
